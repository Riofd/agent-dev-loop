# 🤖 Agent Dev Loop

**多 Agent 协作自动化代码开发框架**

让不同的 AI 模型各司其职，模拟真实开发团队中的角色分工：有人做规划、有人写代码、有人做评审——通过对抗性评审循环持续提升代码质量，最终输出结构化的开发文档。

---

## 🎯 解决什么问题

- 需求拆解全靠脑子想，边界不清、依赖混乱？
- AI 一次生成太多代码，bug 一箩筐，review 无从下手？
- 代码写完了接口文档还欠着，后来者只能靠猜？
- 多 AI 协作时上下文暴涨到失控，不知道在哪一步卡住了？

**Agent Dev Loop 把大需求切成小模块，每块独立开发、独立评审、独立测试，全流程可审计、可恢复。**

---

## 🧭 核心流程

```
需求输入 → 任务规划（对抗评审）→ 代码实现 → 多 Agent 评审 → 开发文档 → 下一模块
   ↑
   ←─────────────────── 异常退出？依赖 devdoc 恢复 ─────────────────────────────┘
```

### Phase 1：任务规划循环

1. **任务规划 Agent**（deepseek-v4-pro）分析需求，拆分为 IO 清晰、边界明确、可独立测试的子功能模块
2. **方案评审 Agent**（GPT-5.5）对规划进行对抗性评审，提出边界、依赖、测试性方面的问题
3. 任务规划 Agent 逐条回复，修订方案
4. 循环直至双方无实质分歧 → 方案写入 `xxx_devdoc.md`

### Phase 2：代码实现循环（每个模块）

1. **代码编写 Agent**（glm-5.1）实现单一模块，严格遵循代码规范
2. **评审 Agent A**（glm-5.1）+ **评审 Agent B**（GPT-5.5）并行独立评审
3. **评审专家 Agent**（deepseek-v4-pro）综合裁定，输出最终评审意见
4. 两个评审 Agent 对裁定结果表态（接受/不接受）
5. 代码编写 Agent 按意见修改 → 重新评审
6. 收敛后写入开发文档 → 开始下一个模块

### Phase 3：开发文档自动沉淀

每个模块完成后，`xxx_devdoc.md` 自动包含：
- 模块 I/O 说明与调用方法
- 测试用例与测试结果
- 前后交互逻辑与依赖关系
- 评审意见与修改记录

## 🏗️ Agent 角色架构

| 角色 | 默认模型 | 职责 |
|------|---------|------|
| 任务规划 Agent | deepseek-v4-pro | 需求分析、任务拆分 |
| 方案评审 Agent | GPT-5.5 | 对抗评审、识别规划缺陷 |
| 代码编写 Agent | glm-5.1 | 单模块实现、代码质量 |
| 评审 Agent A | glm-5.1 | 效率/性能维度评审 |
| 评审 Agent B | GPT-5.5 | API/边界/可维护性评审 |
| 评审专家 | deepseek-v4-pro | 综合裁定、最终决策 |

> **模型可灵活配置**：可根据实际可用的模型和场景，在激活 skill 时动态指定各角色的模型。

## ⚙️ 代码质量要求

- **算法效率**：避免高量级多重循环，数据工程优先使用 numpy / numba / pandas
- **Warning 即 Bug**：任何 Warning 都要认真对待
- **异常处理**：只捕获值得捕获的异常，拒绝空 `except`
- **日志规范**：精简精准，记录关键路径、输入维度、输出维度
- **代码整洁**：修改时同步清理废弃逻辑，不留技术债
- **测试覆盖**：逻辑原理验证 + I/O 边界验证 + 压力测试

---

## 🛡️ 抗干扰与可恢复性

- **上下文管理**：单模块开发上下文控制在 100k tokens 以内，超限自动 compact
- **DevDoc 记忆**：所有关键决策、评审意见、开发状态都写入 `xxx_devdoc.md`
- **异常恢复**：任何 Agent 因网络/模型问题中断后，可依赖 devdoc 从上一个稳定 checkpoint 恢复
- **评审收敛机制**：评审循环超过 5 轮未收敛，由评审专家强制裁定

## 🚀 使用方式

在 OpenClaw 中激活 skill：

```
/skill agent-dev-loop
```

激活时提供：
- **项目名称**：用于命名 devdoc 和目录
- **用户需求**：要开发的功能描述
- **模型配置**（可选）：覆盖默认模型分配
